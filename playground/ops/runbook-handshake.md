# 握手失败排查手册

适用情况：收到"握手失败率高"告警，或者用户报 `QHE-2xx` 错误码。

握手是会话建立的第 2 步：发起方发 `QHP-HELLO` 带上自己的能力字 `qhx`，对端回 `QHP-HELLO-ACK` 带上交集。交集为空就失败（见 `notes/handshake.md`）。

这份手册按"先确认范围、再按错误码分支、最后才翻详细日志"的顺序写。请按顺序走，不要跳步。经验上，八成以上的握手问题在第 2 步就能定位。

## 第 0 步：确认范围

先搞清楚是"所有人都失败"还是"某几个对端失败"：

- 所有人都失败：多半是 qhpd 这边的配置改坏了，先看最近有没有人改过 `/etc/qhp/qhpd.toml`
- 只有某几个对端失败：多半是这几个对端自己的配置问题，或者它们走的链路有问题

看监控指标 `qhp_establish_fail_total{step="handshake"}` 的曲线，突然跳高一般对应一次变更。可以把曲线跳高的时间点和变更记录对一下：配置发布、网关升级、新客户端上线，这三类最常见。

如果同一时间探活、票证交换的失败也在涨，说明问题不在握手本身，可能是网络或者 qhpd 进程出了问题，先去看 `qhpctl status` 和系统负载。

## 第 1 步：看失败分布

```text
$ qhpctl trace --step handshake --last 50
```

重点看两列：`PEER`（哪些对端在失败）和 `CODE`（报的什么错误码）。如果失败集中在少数几个对端，记下它们的地址，后面逐个查。

几个常见的分布形态：

- 失败的对端地址都在同一个网段：先问这个网段最近有没有变更
- 失败的对端都是同一种客户端（比如都是压测工具）：看这种客户端的能力字配置
- 失败是间歇的，同一个对端时好时坏：多半和链路有关，比如经过网关和不经过网关两条路

## 第 2 步：按错误码分支

### QHE-203：能力字交集为空

1. 看 qhpd 这边的能力字：`/etc/qhp/qhpd.toml` 里的 `qhx`，默认是 `txt,bin,hb,ack`
2. 看对端的能力字：SDK 默认声明 `txt,bin,hb,ack`；自己写的客户端、监控探针、压测工具可能只声明了一部分，常见配置见附录 A
3. 两边逐项比对，确认至少有一个相同的短名。注意短名区分大小写，`TXT` 和 `txt` 不是同一个

如果两边比对下来明明有交集，还是报 `QHE-203`，继续看第 3 步。

### 握手阶段超时

如果失败记录显示的是等待 `QHP-HELLO-ACK` 超时，而不是 `QHE-203`，说明请求发出去了但没收到回应：

1. 先确认对端进程是否存活
2. 再看网络：同一个对端的探活是否也在失败（`qhpctl trace --step probe`）。探活也失败，说明是网络或准入名单问题，和握手本身无关
3. 超时和重试规则见 `notes/timeout.md`，重试用完会报 `QHE-900`

## 第 3 步：是否经过网关

很多客户端是经网关（4722）接入的，不是直连 qhpd（4721）。

对比测试：让出问题的对端临时直连 qhpd 的 4721，再握手一次。

- 直连也失败：问题在两端的配置，回到第 2 步
- 直连成功、经网关失败：问题在网关，先看网关版本（`qhpctl gw status`），再看附录 B 的已知问题

做对比测试前要确认这个对端在 qhpd 的准入名单里，否则直连时探活就过不去，会误以为直连也失败。

## 第 4 步：打开详细日志

上面几步都没有结论时，临时打开 `debug` 日志，抓一次完整的握手过程：

```text
$ qhpctl loglevel debug
```

`debug` 日志里会打印 `QHP-HELLO` 和 `QHP-HELLO-ACK` 里的完整 `qhx`。抓到以后切回 `info`，`debug` 日志量很大。

如果问题和网关有关，网关那边也要抓：网关的日志在 `/var/log/qhp/gw.log`，网关的日志级别同样可以在线调整。

## 第 5 步：恢复确认

处理完以后：

1. `qhpctl trace --step handshake --last 20` 确认最近的握手都成功
2. 观察 `qhp_establish_fail_total{step="handshake"}` 15 分钟，确认不再增长
3. 告警自动恢复后，在告警群里写明原因和处理方式

## 需要升级处理的情况

遇到下面几种情况，不要自己硬查，按 `ops/oncall.md` 升级给协议组：

- 按手册走完所有步骤，仍然没有定位
- 需要修改线上 qhpd 的 `qhx` 配置（会影响所有客户端）
- 怀疑是 qhpd 或网关本身的程序问题，而不是配置问题

## 历史案例

下面是这份手册整理以来遇到过的几次典型问题，排查时可以对照。

### 案例 1：改配置忘了改回来

- 现象：某天下午所有使用 `txt` 帧的客户端握手失败，报 `QHE-203`
- 排查：第 0 步发现是"所有人都失败"，查变更记录，上午有人为了测试把一台 qhpd 的 `qhx` 改成了 `bin`
- 原因：测试完没有改回来，只声明 `bin` 的 qhpd 和只用 `txt` 的客户端没有交集
- 处理：改回 `txt,bin,hb,ack`，`qhpctl reload` 生效。之后规定线上 qhpd 的 `qhx` 只能通过配置发布修改

### 案例 2：跨机房握手超时

- 现象：新机房的一批客户端握手阶段超时，重试用完后报 `QHE-900`
- 排查：第 2 步发现探活也在失败，说明不是握手本身的问题
- 原因：新机房到实验室的网络策略漏开了 4721 端口
- 处理：网络组补开端口后恢复。这个案例说明"握手失败"告警不一定是握手的问题

### 案例 3：客户端把能力字写成了大写

- 现象：一个新上线的内部工具握手一直失败，报 `QHE-203`，其他客户端都正常
- 排查：第 2 步比对能力字，工具声明的是 `TXT,BIN`
- 原因：短名区分大小写，大写的 `TXT` 和 qhpd 的 `txt` 不匹配，交集为空
- 处理：工具改成小写后恢复

### 案例 5：配置发布只发了一半

- 现象：同一个客户端连某几台 qhpd 握手成功，连另外几台报 `QHE-203`
- 排查：第 1 步看失败分布，失败集中在 3 台 qhpd 上；逐台看 `qhpd.toml`，这 3 台的 `qhx` 还是旧值
- 原因：一次配置发布中途失败，只有一部分机器拿到了新配置
- 处理：重新发布配置，逐台 `qhpctl check-config` 后 `qhpctl reload`。之后配置发布增加了"发布完逐台核对"这一步

### 案例 6：压测工具升级后少声明了一项

- 现象：压测期间握手失败率突然升到 30% 以上，触发告警，线上业务客户端都正常
- 排查：第 0 步确认只有压测流量失败；第 2 步看压测工具的能力字，升级后的版本默认只声明 `bin`
- 原因：那次压测针对的是一组只开了 `txt,hb,ack` 的测试节点，和只声明 `bin` 的压测工具没有交集
- 处理：压测工具显式配置 `txt,hb,ack`。教训是压测前先用一个客户端手工握手一次，确认能通再放量

### 案例 4：监控探针经网关失败

- 现象：老的监控探针经网关连 qhpd 时报 `QHE-203`，直连 qhpd 正常；两边配置文件都检查过，没有问题
- 排查：第 3 步对比测试，确认问题在网关
- 原因和处理：见附录 B

## 常见问答

**Q：`QHE-203` 会自动重试吗？**
不会。能力字交集为空是确定性的失败，重试多少次结果都一样，所以直接结束，不进入票证交换。

**Q：能不能让 qhpd 接受所有能力字，省得配错？**
不能。能力字的作用就是让双方确认"我们说的是同一套帧"，全部接受等于没有检查。

**Q：握手失败会影响已经建立的会话吗？**
不会。握手失败只影响正在建立的那一次，已经锁定的会话不受影响。

**Q：改了 qhpd 的 `qhx`，已经建立的会话会重新握手吗？**
不会。`qhpctl reload` 只影响之后新建立的会话，已经锁定的会话继续按原来协商好的能力字工作，直到拆除。

**Q：握手失败率告警的阈值为什么是 20%？**
少量握手失败是正常的，比如有人拿错配置的客户端试连。阈值太低会频繁误报，太高又会漏掉真正的问题。20% 是运行一段时间以后定下来的，具体规则见 `ops/alerts.md`。

**Q：排查完要写记录吗？**
要。在告警群里写明现象、原因、处理方式三件事，下面是模板。

## 附录 B：已知问题

**网关 1.0.0 到 1.1.1：转发握手时丢掉 `ack`**

这几个版本的网关在转发 `QHP-HELLO` 时，会把发起方 `qhx` 里的 `ack` 去掉，再交给上游。

大多数客户端不受影响：去掉 `ack` 以后，`txt`、`bin`、`hb` 还在，交集不会为空。但只声明了 `ack` 的发起方（比如老的监控探针）就会出问题：`ack` 被去掉后它的能力字是空的，交集为空，上游报 `QHE-203`。

这个问题很难查，因为两边的配置文件看起来都没问题，直连 qhpd 也一切正常。

- 根本解决：把网关升级到 **1.1.2**
- 临时绕过：让这类探针直连 qhpd 的 4721，不经过网关
